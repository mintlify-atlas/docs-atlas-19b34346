Remote mode lets you run the `omniroute` CLI on your laptop while OmniRoute itself runs on a VPS, a home server, or another machine on your Tailnet. Log in once with `omniroute connect` and every subsequent CLI command targets that remote server — same commands, same output, same experience. There is no second tool to install: remote mode is the regular `omniroute` CLI plus scoped access tokens.

```bash
npm install -g omniroute                 # the normal CLI install
omniroute connect 192.168.0.15           # log in (password → scoped token, saved as a context)
omniroute models list                    # now lists the REMOTE server's models
omniroute configure codex                # picks a remote model, writes local Codex profile
```

---

## How It Works

```text
your laptop                              remote OmniRoute (VPS)
┌────────────────────┐                   ┌───────────────────────────────┐
│ omniroute CLI      │  POST /api/cli/connect  (password → token)         │
│  context: vps      │ ──────────────►  │ mints a scoped access token    │
│  baseUrl, token    │  Authorization: Bearer oma_live_…                  │
│                    │ ──────────────►  │ every management route, scope- │
│ writes configs     │ ◄──────────────  │ checked per the token's scope  │
│ LOCALLY            │                   └───────────────────────────────┘
└────────────────────┘
```

- **Contexts** store one server each (`~/.omniroute/config.json`, mode `0600`). `omniroute contexts use <name>` switches the active server; `default` is the local instance.
- **Access tokens** (`oma_live_…`) authorize management commands. They are distinct from inference API keys (`sk-…`) used for `/v1/chat/completions`.
- Only the SHA-256 hash of a token is stored server-side. The plaintext is shown **once**, at creation.

## Connecting

### With the Management Password

The password flow mints an **admin** token by default and saves it as a context:

```bash
omniroute connect 192.168.0.15
# Management password for http://192.168.0.15:20128: ********
# ✔ Connected to http://192.168.0.15:20128 — context '192.168.0.15' (scope: admin)
```

A full HTTPS URL is accepted as-is:

```bash
omniroute connect https://my-omniroute.example.com
```

Options:
- `--port <p>` — specify the port when the host address has none
- `--name <ctx>` — custom context name
- `--scope read|write|admin` — downscope the minted token

### With a Pre-Generated Token

Generate a scoped token in the dashboard (or with `omniroute tokens create`) and connect without a password:

```bash
omniroute connect 192.168.0.15 --key oma_live_xxxxxxxx
```

The CLI validates it via `GET /api/cli/whoami` and saves it as the active context.

## Running Commands Against the Remote

Once connected, every CLI command targets the remote server transparently:

```bash
omniroute models list          # runs against the REMOTE server
omniroute configure codex      # picks a remote model, writes local Codex profile
omniroute combo list           # lists combos on the remote
```

<Note>
  Config files (`~/.codex/*.config.toml`, `~/.claude/profiles/*/settings.json`, etc.) are always written **locally** on your laptop. The remote server supplies the model catalog and API endpoint; your machine holds the tool configuration.
</Note>

## Token Management

Tokens require an **admin** credential to create, list, or revoke. You can also manage them in the dashboard under **Settings → Access Tokens**.

```bash
omniroute tokens create --name ci --scope read   # mint a narrower read-only token
omniroute tokens list                             # masked: id, name, scope, prefix, status, expiry
omniroute tokens revoke <token-id>                # revoke immediately
omniroute tokens scopes                           # explain the three scope levels
```

<Tip>
  For CI/CD pipelines, always use `--scope read`. Revoke the token as soon as the pipeline no longer needs it.
</Tip>

### Token Scopes

Three levels, hierarchical (`admin ⊃ write ⊃ read`):

| Scope | Capabilities |
|---|---|
| `read` | List and inspect — `models list`, `providers status`, `logs`, `usage`, `cost` |
| `write` | Read **+** configure and apply — `setup-codex`, `keys add`, `config set`, combos |
| `admin` | Write **+** manage — `tokens` CRUD, add providers, services, policy, OAuth |

The server infers the required scope from the HTTP method (`GET` → `read`, mutations → `write`) plus an admin allowlist for sensitive surfaces (`/api/cli/tokens`, `/api/providers` mutations, `/api/oauth`, `/api/services`). A token with insufficient scope gets `403` with a clear message.

## Context Switching

A **context** is a saved server (base URL + credential + scope). `omniroute connect` creates one and makes it active. Use `omniroute contexts` to inspect and switch between them:

```bash
omniroute contexts list            # all contexts; the active one is marked ●
omniroute contexts current         # the active server, auth status, and scope
```

Example output:

```text
  | Name    | Base URL                  | Auth  | Scope | Description
● | vps     | http://100.67.86.91:20128 | token | admin | Remote OmniRoute
  | default | http://localhost:20128    | ✗     |       |
```

Switch the active server — every subsequent command follows:

```bash
omniroute contexts use my-vps      # → all commands now hit the remote
omniroute tokens list              #   (runs against the VPS)

omniroute contexts use default     # → back to localhost
omniroute tokens list              #   (runs against the local server)
```

Add a context manually, inspect, or rename:

```bash
omniroute contexts add staging \
  --url https://staging.example.com:20128 \
  --access-token oma_live_xxxx \
  --scope write \
  --description "staging box"

omniroute contexts show staging    # full details for one context
omniroute contexts rename staging stg
```

Remove a context (prompts for confirmation; use `--yes` in scripts):

```bash
omniroute contexts remove stg --yes
```

<Note>
  The `default` (localhost) context cannot be removed. Removing the active context automatically falls back to `default`. Removing a context only drops the **local** saved credential — revoke the token on the server with `omniroute tokens revoke <id>` to actually kill access.
</Note>

## Configuring Coding CLIs from the Remote Catalog

`omniroute configure` reads the **active server's** live model catalog and writes the config file on **your** machine:

```bash
omniroute configure codex
#   Providers: glm, kmc, ollamacloud, opencode-go, …
#   Provider: glm
#   Model id: glm/glm-5.2
#   ✔ Wrote ~/.codex/glm52.config.toml
#   Use it:  codex --profile glm52

# Non-interactive
omniroute configure codex --provider glm --model glm/glm-5.2 --name glm52

# Pin a favorite at the top of the interactive picker
omniroute configure codex --provider glm --model glm/glm-5.2 --favorite --yes
```

The model picker never writes URLs or credentials to disk — only model IDs, scoped by context and CLI target.

## Quick End-to-End Lifecycle

Copy-paste workflow to verify a remote setup from scratch — connect, mint a scoped token, run a command, switch back, and tear down:

<Steps>
  <Step title="Connect with the management password">
    ```bash
    omniroute connect 192.168.0.15
    omniroute contexts current        # confirm the remote server + scope
    ```
  </Step>
  <Step title="Use the remote">
    ```bash
    omniroute tokens create --name laptop --scope read
    omniroute tokens list             # runs against the VPS
    ```
  </Step>
  <Step title="Switch back and forth">
    ```bash
    omniroute contexts use default    # → local
    omniroute contexts use 192-168-0-15  # → remote (name from contexts list)
    ```
  </Step>
  <Step title="Tear down">
    ```bash
    # Revoke server-side FIRST to actually kill access
    omniroute tokens revoke <id|prefix>

    # Then drop the local saved context
    omniroute contexts remove 192-168-0-15 --yes
    ```
  </Step>
</Steps>

## Loopback-Only Routes

Routes that spawn processes (`/api/services/*`, `/api/mcp/*`) stay **loopback-only** even when a remote token is present. A remote token with `admin` scope cannot reach these routes — they require a request that originates on the server's own loopback interface. This is by design and cannot be overridden by scope alone.

## Security Notes

<CardGroup cols={2}>
  <Card title="Use HTTPS or a Tailnet" icon="lock">
    A bare `omniroute connect 192.168.0.15` defaults to `http://` for LAN/Tailscale convenience. Pass a full `https://…` URL for TLS in production.
  </Card>
  <Card title="Token storage" icon="key">
    Token plaintext is shown once. Only the SHA-256 hash is persisted server-side. Tokens are stored in the OS keychain (`keytar`) when available; headless installs fall back to `config.json` with mode `0600`.
  </Card>
  <Card title="CI/CD tokens" icon="shield">
    Always mint `--scope read` tokens for CI/CD pipelines. Revoke them when the job is done. Never reuse long-lived admin tokens across environments.
  </Card>
  <Card title="Brute-force protection" icon="ban">
    `omniroute connect` reuses the server's login brute-force lockout and audit logging. Failed password attempts are rate-limited and logged.
  </Card>
</CardGroup>

## API Endpoints Reference

| Method | Route | Auth | Scope |
|---|---|---|---|
| `POST` | `/api/cli/connect` | Management password | — (public, password-gated) |
| `GET` | `/api/cli/whoami` | Access token | `read` |
| `GET` | `/api/cli/tokens` | Access token | `admin` |
| `POST` | `/api/cli/tokens` | Access token | `admin` |
| `DELETE` | `/api/cli/tokens/:id` | Access token | `admin` |
